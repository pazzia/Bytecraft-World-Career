# Релизы Android и ключ подписи

CI собирает APK на каждый PR и на каждый пуш в `main`. Сборки из `main` публикуются в **Releases** репозитория.

Android обновляет установленное приложение, только если у нового APK **та же подпись** и **больший номер версии**:
- номер версии CI ставит сам, это номер запуска CI (`--build-number=${{ github.run_number }}`);
- подпись — постоянный ключ, который хранится в кэше GitHub Actions.

## Где живёт ключ

Ключ (`release.jks` и пароль к нему) лежит в кэше GitHub Actions под именем `bytecraft-signing-v1`. Ничего настраивать не нужно:

1. Первая сборка в `main` не находит ключ в кэше, создаёт его (RSA 4096, alias `bytecraft`) и сохраняет в кэш.
2. Все следующие сборки берут ключ из кэша, поэтому новые версии ставятся поверх старых.
3. Сборки в PR тоже берут ключ из кэша `main`. Пока ключа нет, PR подписывается одноразовым ключом.

Отпечаток сертификата (SHA-256) печатается в описании каждого релиза и в разделе **signing** комментария CI к PR. Если у двух релизов отпечатки разные, второй не встанет поверх первого.

Первая сборка с постоянным ключом не встанет поверх старых сборок (они подписаны одноразовыми ключами): их нужно один раз удалить. Об этом написано в описании такого релиза.

## Как ключ не потерять

GitHub удаляет запись кэша, если её не использовали 7 дней. Чтобы этого не случилось, workflow **Keep signing key** (`.github/workflows/keep-signing-key.yml`) читает ключ из кэша раз в два дня. Если ключа там нет, запуск падает с ошибкой, и GitHub пришлёт письмо.

Ограничения, о которых стоит знать:
- GitHub отключает расписания в репозитории, где 60 дней не было коммитов. Если проект надолго заброшен, перед возвращением откройте **Actions → Keep signing key** и включите workflow.
- Не удаляйте кэш `bytecraft-signing-v1` на странице **Actions → Caches**. Новый ключ уже не обновит установленное приложение.
- Кэш виден workflow этого репозитория, в том числе из PR. Это приемлемо для приложения, которое вы ставите себе сами. Перед публикацией в Google Play нужен отдельный upload-ключ в GitHub Secrets; CI уже умеет его брать (см. ниже).

Если ключ всё же пропал, следующая сборка в `main` создаст новый. Установленное приложение придётся один раз удалить и поставить заново; прогресс в игре при этом сбросится.

## Ключ из GitHub Secrets (на будущее)

Если в репозитории заданы секреты, CI подписывает ими, а не ключом из кэша:

| Имя | Значение |
|-----|----------|
| `ANDROID_KEYSTORE_BASE64` | файл `.jks` в base64 |
| `ANDROID_KEYSTORE_PASSWORD` | пароль хранилища |
| `ANDROID_KEY_ALIAS` | alias ключа |
| `ANDROID_KEY_PASSWORD` | пароль ключа (у PKCS12 совпадает с паролем хранилища) |

Это понадобится для Google Play: там же нужен AAB (`flutter build appbundle`), это отдельный шаг в CI.

## Версия сборки

Номер версии берётся из `pubspec.yaml` (`version: 0.1.0+1`, часть до `+`), номер сборки — номер запуска CI. Оба видны внизу экрана «Профиль» («Bytecraft 0.1.0 (сборка 21)»), в названии релиза и в имени файла APK (`bytecraft-0.1.0-build21.apk`).

## Что ещё нужно знать

- Старое приложение CodeQuest имеет другой идентификатор (`com.pazzia.codequest_mvp`) и Bytecraft (`com.pazzia.bytecraft`) не обновит. Его можно просто удалить.
