# Bytecraft, «Журнал»: ревью подачи тем и стандарт для авторов

Источники: `assets/content/python/topics.json` (106 тем, прочитаны все), `tool/content/bclib.py` (`topic()`), `lib/features/journal/presentation/widgets/topic_content.dart`, `topic_screen.dart`, `shared/widgets/code_block.dart`, `output_board.dart`, `core/theme/*`, шрифты `assets/fonts/*` (покрытие глифов проверено через fontTools). В проекте ничего не менялось.

## 1. Диагноз

### 1.1. Проблемы по типам

**А. Тело темы — «стена» абзацев без структуры.** Виджет режет `body` по пустой строке и рисует каждый кусок одним `Text(bodyLarge)`. Заголовков, списков, выделения кода нет, поэтому глаз не за что зацепить.
- 18 абзацев длиннее 280 символов. Рекордсмены: `idiom_match` (525 символов в одном абзаце: список из 8 видов шаблонов внутри одного предложения), `conc_processes` (502), `proj_cli_logging` (460), `conc_threads` (447), `algo_patterns` (381), `inh_mro` (376), `inh_basics` (343), `exc_raise` (336).
- Перечисления, которые просятся в список или таблицу, записаны прозой: режимы файлов (`files_open`), токены регулярок (`data_re`), опции `@dataclass` (`dc_basics`), методы `add_argument` (`proj_cli_logging`), assert-методы (`test_unittest`), 5 классов `collections` (`std_collections`), цена операций (`algo_complexity`), спецификация формата (`io_format`, `str_fstring`), соответствие типов (`data_json`).
- 8 тем длиннее 900 символов без единого подзаголовка: `async_tasks` (1550), `conc_processes` (1470), `proj_cli_logging` (1377), `conc_threads` (1350), `proj_structure` (1102), `async_basics` (957), `gen_yield` (950), `test_assert` (913).

**Б. Код внутри текста не отличается от русского текста.** Ни в одном `body` нет разметки кода (0 из 106). Отсюда неоднозначности:
- непонятно, где кончается код: `x = 5 читается справа налево` (`var_assign`), `-7 // 2 == -4.` (точка от предложения или от числа?) (`ops_arith`);
- кавычки сливаются с текстом: `split(" ") режет строго по одному пробелу: "a  b".split(" ") даёт ['a', '', 'b']` (`str_methods`); `'{"a": 1}' — правильно, "{'a': 1}" — json.JSONDecodeError` (`data_json`);
- операторы теряются: `| — объединение, & — пересечение, - — разность` (`set_ops`): дефис-оператор рядом с тире-пунктуацией читается как опечатка;
- шаблоны без кода не видны: `if items is None: items = []` идёт отдельной строкой абзаца (`args_mutable_default`) и рендерится пропорциональным шрифтом без отступов.

**В. Символы, которых нет в шрифте, превращаются в эмодзи или «тофу».** Проверено по cmap бандла:
- `↔` (U+2194) в Onest отсутствует. На Android срабатывает fallback на Noto Color Emoji, потому что у символа есть свойство Emoji. Отсюда «квадратики» в `data_json` (5 вхождений).
- `⇒` (U+21D2) в Onest тоже нет: `dunder_ops`, «a == b ⇒ hash(a) == hash(b)».
- `→` (U+2192) в Onest есть, 13 вхождений рисуются нормально (`dict_basics`, `scope_legb`, `std_import`, `data_datetime`, `gen_lazy`, `typing_advanced`, note в `loop_while`). Стрелка всё равно спорная: в `std_import` «import math → math.sqrt(16)» она стоит между двумя фрагментами кода и выглядит как оператор.
- `ⁿ`, `∞`, `√`, `‑` (неразрывный дефис) в Onest тоже отсутствуют. В текстах их пока нет, но защиты от них нет.

**Г. Примеры трудно читать на телефоне.**
- Код рисуется размером 18 (размер для игровых уровней) с колонкой номеров строк. На экране 360 dp видно примерно 24 символа. 329 из 914 строк кода (36%) длиннее и уезжают в горизонтальный скролл, 72 строки длиннее 48 символов. Худшие: `proj_cli_logging` (106), `idiom_match` (103), `algo_search_sort` (102), `dunder_ops` (97).
- 37 строк печатают 4 и больше значений одним `print(a, b, c, d)`, и вывод нельзя сопоставить с выражением. Пример `dunder_ops`: `print(Vec(1, 2) + Vec(3, 4), Vec(1, 1) == Vec(1, 1), len({...}), Vec(1, 1) == 5)` даёт `Vec(4, 6) True 1 False`. Та же картина в `ops_precedence`, `str_index`, `types_convert`, `loop_range`, `set_ops`, `prop_classmethod`.
- У 81 из 144 примеров нет `note`, поэтому заголовок у них «Пример 2», а это не информация.
- 69 тем из 106 держатся на одном примере. Часто он показывает только исправление и не показывает саму проблему: `args_mutable_default` демонстрирует правильный `None`, но не баг. Бывает, что пример не про тему: первый пример `loopx_nested` не содержит вложенного цикла, и note сам это признаёт.
- Код и вывод — две разные «доски» с разным радиусом и рамкой, а между ними подпись «Вывод». Визуально это два несвязанных блока.

**Д. Summary не выполняет роль «сути».**
- 21 summary длиннее 140 символов. `conc_threads` — 317 символов в трёх предложениях со скобками, дальше идут `perf_tricks` (222), `async_tasks` (217), `test_logging` (205).
- Вместо сути часто стоит перечень имён: `str_methods`, `std_itertools`, `std_collections`, `perf_tricks`, `fn_builtins`. Встречается и пустая фраза: `dict_methods` — «get, keys, values, items, pop, update, setdefault — основные операции».
- Summary повторяется первым предложением body: `str_methods` («Методы не меняют строку» дважды), `files_read`, `dict_counting`.

**Е. Частые ошибки без исправления и с повторами.**
- 176 пунктов, в среднем 1,7 на тему. Многие описывают только ошибку, без правильного варианта: `str_basics` («Пытаться изменить символ строки по индексу.»), `tuple_basics`, `set_ops`, `comp_list`, `cond_ternary`, `inh_mro`.
- Часть ошибок — дословный повтор body: `types_basic` (оба пункта), `list_mutable`, `set_basics`, `idiom_eafp`.
- Перед каждым пунктом одинаковая оранжевая иконка warning. При 3–4 пунктах она превращается в шум, и ошибка визуально не отличается от совета.
- Наоборот, содержательное иногда живёт только в ошибках: `round()` и банковское округление (`types_convert`), `x == 1 or 2` (`cond_logic`), оптимизация хвостовой рекурсии (`rec_memo`).

**Ж. Термины и отсылки без объяснения и без перехода.**
- Термин появляется раньше своей темы и не объясняется. «Хешируемый» встречается в `tuple_basics`, `set_basics`, `dict_basics`, `rec_memo`, `dunder_ops`, `perf_tricks`, но отдельного объяснения нет нигде. «Поверхностная копия» в `list_mutable` без пояснения. «Колбэк» (`fn_functools`), «ленивый» (`comp_dict_set` до темы о генераторах), `isinstance` (`rec_structures` до ООП), `type(x).__name__` (`types_basic`, 2-й модуль).
- Ручные отсылки ломаются при перестановке модулей: «в модуле 10» (`loopx_enumerate`), «в отдельном модуле» (`loop_range`, `rec_memo`, `prop_property`, `inh_mro`), «о них дальше» (`types_bool`), «в модуле про ООП» (`exc_raise`), «в модуле „Программа как проект“» (`conc_processes`), «в модуле „Тестирование и отладка“» (`proj_cli_logging`). Всё это должно стать ссылками.

**З. Темы-«ящики».** В одной карточке собрано 3–7 самостоятельных тем, и при раскрытии каждой она станет нечитаемой:
- `async_tasks`: gather, create_task, TaskGroup, таймауты, Lock, Semaphore, Queue;
- `algo_patterns`: куча, BFS, окно, два указателя;
- `inh_mro`: MRO, ABC, Protocol;
- `typing_advanced`: Protocol, дженерики, TypedDict, Literal;
- `std_collections`: 7 классов;
- `idiom_walrus`: `:=`, звёздочная распаковка, `f"{x=}"`;
- `proj_structure`: `__main__`, PEP 8, docstring, пакеты, venv.

**И. Тон разнобойный.** В основном текст нейтральный, советы — в повелительном наклонении на «вы» («оберните», «указывайте», «проверяйте», «не называйте», «перебирайте»). Но местами встречается «мы»: «заводим total», «делим число» (`loop_for`, `loop_while`), «обрабатываем его» (`rec_structures`), «разберём в отдельном модуле» (`prop_property`), «ищем в цикле» (`loopx_else`).

**К. Экран темы.** Над текстом стоят кнопка «Сохранить в журнал» или карточка повторения. На первом экране содержимого остаётся мало, и суть уезжает вниз.

### 1.2. Пробелы курса (темы нет, а термин используется)

- Чтение трассировки ошибки (traceback). Новичок видит её постоянно, а в курсе её нет.
- `None` как значение. Упоминается в 20+ темах, но своей темы нет.
- Хешируемость.
- `del` и `pass`.
- Глубокая копия (`copy.deepcopy`).
- Модули `random` и `math`: используются, но описаны одной строкой в `std_import`.

Для хешируемости, `None`, `pass` и `del` достаточно статей глоссария (см. §4.3). Для трассировки нужна полноценная тема в модуле «Исключения».

### 1.3. Все 106 тем: полнота и понятность

Без замечаний по содержанию (нужна только переразметка по §2–3): `var_multi`, `types_bool`, `str_index`, `io_input`, `cond_ternary`, `loop_for`, `loop_range`, `loopx_break`, `dict_counting`, `comp_cond`, `func_params`, `args_unpack`, `fn_lambda_key`, `rec_basics`, `rec_structures`, `rec_memo`, `files_open`, `files_read`, `files_csv`, `std_import`, `oop_class_attrs`, `inh_poly`, `dunder_str`, `prop_classmethod`, `prop_private`, `dc_enum`, `ctx_contextlib`, `typing_basics`, `algo_complexity`, `perf_measure`, `async_basics` — 31 тема.

## 2. Стандарт подачи темы

### 2.1. Структура карточки (сверху вниз)

| Порядок | Поле | Что это | Обязательно |
|---|---|---|---|
| 1 | `title` | Название темы | да |
| 2 | `summary` | Суть одним предложением | да |
| 3 | `body`: вводный абзац | Зачем это нужно, какую задачу решает | да |
| 4 | `body`: разделы `##` | Синтаксис, как работает, тонкости, выбор | если body > 2 абзацев |
| 5 | `examples` | 2–4 примера от простого к сложному | да |
| 6 | `pitfalls` | 1–4 ошибки в виде «так нельзя / так можно» | да |
| 7 | «Связанные темы» | Собирается автоматически из ссылок | — |
| 8 | «Практика» | Как сейчас | — |

**Заголовок.** До 32 символов (две строки при 24 sp). Это название вещи, а не перечень. Вместо «Включения для словарей и множеств, генераторные выражения» — «Включения для словарей и множеств», а генераторное выражение уходит в `gen_yield` или `gen_lazy`. Вместо «map, filter, zip, enumerate, any, all» — «Функции для последовательностей».

**Summary.** Одно предложение, до 120 символов. Формула: «X — это / делает Y[, чтобы Z]». Без перечня имён, без скобок, без ссылок. Код в бэктиках разрешён. Первое предложение body не должно повторять summary.
- Плохо: «get, keys, values, items, pop, update, setdefault — основные операции.»
- Хорошо: «Методы словаря читают значения без KeyError, перебирают пары и меняют словарь целиком.»

**Вводный абзац.** 1–3 предложения: где это встречается в реальной программе и какую боль снимает. Без синтаксиса.

**Разделы.** Набор ролей фиксирован, тексты заголовков конкретные:

| Роль | Заголовок | Когда |
|---|---|---|
| Синтаксис | `## Как записать` (всегда этими словами) | у темы есть конструкция языка |
| Механизм | Конкретное утверждение: «Как Python выбирает ветку», «Что значит @» | всегда |
| Тонкости | Конкретное: «Строгий синтаксис», «Ключи становятся строками» | при наличии |
| Выбор | `## Что выбрать` (всегда этими словами) | есть альтернативы (`sort`/`sorted`, потоки/процессы) |

Обезличенные «Описание», «Особенности», «Важно», «Примечание» запрещены. Заголовок раздела — до 32 символов, без точки.

**Бюджет длины.**
- body: 400–1400 символов. Больше 1600 — тему делят. `async_tasks`, `conc_processes`, `conc_threads`, `proj_cli_logging`, `proj_structure` делятся сразу.
- Раздел: 1–3 абзаца или абзац плюс список.
- Абзац: до 3 предложений и до 280 символов, одна мысль.
- Предложение: до 20 слов. Если в нём больше одного двоеточия или есть скобка внутри скобки — делите.

### 2.2. Список, нумерация, таблица

| Форма | Когда | Пример |
|---|---|---|
| Абзац | Причина и следствие, объяснение «почему» | «Поэтому порядок проверок важен…» |
| `- список` | От 3 однородных пунктов, порядок не важен | режимы `open`, параметры `dumps` |
| `- \`код\` — пояснение` | Словарь «конструкция — что делает» | `- \`d.get(k, 0)\` — значение или 0` |
| `1. нумерация` | Только настоящая последовательность шагов | порядок проверки веток, шаги `for` |
| Таблица | От 3 строк соответствия по 2–3 признакам | Python и JSON, «метод — меняет? — возвращает» |

- Таблица: не больше 3 колонок и 8 строк, ячейка до 24 символов, без предложений внутри. Если ячейке нужно предложение, это список.
- Пункт списка — до 1,5 строки на телефоне (около 70 символов). Пункты грамматически однородны: все начинаются с кода или все с глагола.

### 2.3. Как писать про синтаксис

- Любой фрагмент кода, даже один оператор (`+`, `==`, `:`), ключевое слово (`if`) или значение (`None`, `"0"`), — в бэктиках. Без исключений: это единственный способ снять неоднозначность из §1.1-Б.
- Общий вид конструкции — только в блоке ` ```syntax ` (см. §3). Места, которые подставляет автор, пишутся кириллицей (`условие`, `последовательность`). Рендерер красит кириллические идентификаторы в блоке `syntax` как плейсхолдеры. В курсе это уже принято («[выражение for x in последовательность]»), теперь появится и визуальное отличие.
- Сообщения об ошибках — как в Python, в бэктиках: `TypeError: unhashable type: 'list'`. Имя исключения при первом упоминании — ссылкой (см. §4).
- Версии — коротко в скобках в конце предложения: «(с Python 3.11)». Рассказ об истории версий (`conc_processes`) — только если он меняет поведение кода у читателя.
- Не заканчивайте предложение голым кодом с точкой: «результат — `-4`.» допустимо, потому что чип отделяет точку. А «`-7 // 2 == -4.`» внутри одного чипа — нет.

### 2.4. Примеры

- **Количество:** 2–4, от простого к сложному.
  1. Минимальный: 3–6 строк, один приём.
  2. Типичная задача: как это пишут в жизни.
  3. Граница или ловушка: что бывает, если нарушить правило. Это пример, а не только текст ошибки.
  4. (необязательно) сочетание с ранее пройденным.
- **Объём:** до 14 строк в примере.
- **Ширина строки:** до 32 символов — видно целиком на любом телефоне при коде 15 sp. 33–48 символов — допустимо, строка прокручивается. Больше 48 — переписать: перенести аргументы по строкам, ввести промежуточную переменную.
- **Один `print` — один факт.** Не больше 2 значений в одном `print`, и только если они сравниваются (`print(a, b)` «до и после»). Иначе вывод не сопоставить с кодом.
- **`note` обязателен.** Это заголовок примера, а не комментарий. До 70 символов; говорит, что увидеть в выводе.
  - Плохо: «Пример 2», «То же через lru_cache».
  - Хорошо: «Кортеж вернулся списком, ключ 1 — строкой "1"».
- Данные в примерах — осмысленные (заказ, оценка, сохранение игры), а не `foo` и не `a, b, c`, если тема не про абстракцию.
- Пример должен показывать тему. Если пример про `loopx_nested` не содержит вложенного цикла, это ошибка.
- Вывод считается автоматически; писать его в `note` нельзя, потому что разойдётся.

### 2.5. Частые ошибки: «так нельзя / так можно»

Формат пункта — три поля:
- `bad`: код с ошибкой, 1–4 строки;
- `good`: исправленный код;
- `why`: одно предложение до 120 символов, с текстом ошибки Python, если она есть.

Текстовый пункт без кода допустим, только если ошибка концептуальная («Ждать, что `match` проваливается в следующий `case`»). Тогда это одно предложение с исправлением: «…: срабатывает только первый подходящий `case`».

Правила:
- 1–4 пункта.
- Не повторять body дословно. Ошибка — это то, что пишет новичок, а не правило из текста.
- Содержательное правило не прячется только в ошибках: сначала оно в body, а в ошибке — его нарушение.

Предлагаемая форма в исходниках (`bclib.py`):

~~~python
pitfall(
    "При 95 сработает первая ветка, до проверки на 90 дело не дойдёт.",
    bad='''
        if score >= 50:
            grade = "C"
        elif score >= 90:
            grade = "A"''',
    good='''
        if score >= 90:
            grade = "A"
        elif score >= 50:
            grade = "C"''',
)
~~~

`bad` и `good` не выполняются (это фрагменты), но проходят `ast.parse`, если в `why` не сказано, что это `SyntaxError` (флаг `syntax_error=True`). В JSON это объект `{"why", "bad", "good"}`; старые строковые пункты рендерятся как текстовые.

### 2.6. Тон

Нейтральное изложение плюс обращение на «вы» в советах и ошибках, повелительное наклонение во множественном числе: «указывайте кодировку», «не называйте файл json.py».

Почему так:
1. Так уже написано большинство тем. «Оберните», «проверяйте», «указывайте», «перебирайте», «используйте» встречаются в 10+ темах, «ты» — ни в одной. Смена на «ты» потребовала бы переписать всё.
2. Нейтральная форма короче («Тело пишут с отступом» вместо «Вы пишете тело с отступом»), а на экране 360 dp каждое слово стоит строки.
3. «Вы» — нормальная форма для справочника. Игровой «ты» уместен в интерфейсе уровней, но не в тексте, который перечитывают как документацию.

Запрещено: «мы», «давайте», «разберём», «заметим», «как известно», «очень», «просто» (в значении «легко»), «на самом деле», восклицательные знаки в тексте.

## 3. Разметка body

### 3.1. Синтаксис

Это подмножество GFM Markdown: авторы видят превью в любом редакторе, а Flutter-парсер пишется за день.

| Конструкция | Синтаксис | Где | Рендер |
|---|---|---|---|
| Абзац | Текст, разделитель — пустая строка | body | bodyLarge |
| Заголовок раздела | `## Текст` | body | titleMedium, отступ сверху 28 |
| Список | `- пункт` | body | Маркер-точка, висячий отступ |
| Нумерованный список | `1. пункт` | body | Номер в моноширинном шрифте |
| Код в строке | `` `код` `` | везде, кроме title | Чип: моно 0.88 em, фон |
| Код с бэктиком внутри | ``` `` a`b `` ``` | редко | То же |
| Важно | `**текст**` | body, why | w700, не больше 1 на раздел |
| Ссылка на тему | `[[topic_id\|текст]]` | body, why | Текст цвета primary с подчёркиванием |
| Ссылка-код | ``[[topic_id|`код`]]`` | body, why | Чип с подчёркиванием primary |
| Ссылка на глоссарий | `[[g:term_id\|текст]]` | body, why | Как ссылка, открывает только шторку |
| Синтаксис-шаблон | ` ```syntax ` … ` ``` ` | body | Светлая доска, моно 15, кириллица — плейсхолдер |
| Таблица | `\| a \| b \|` + строка `\|---\|---\|` | body | См. §5.4 |

Внутри текста ссылки `[[…|текст]]` разбираются только бэктики. `**` там не означает жирный, поэтому `[[args_star|*args и **kwargs]]` безопасно. Но лучше писать ``[[args_star|`*args` и `**kwargs`]]``: это код.

Не входит в язык, и правильно:
- `###` — второй уровень на телефоне не читается. Если он нужен, тему надо делить.
- Курсив — кириллица в Onest-italic отсутствует, будет синтетический наклон.
- Цитаты `>` и «плашки» вида «Важно/Совет» — это та же иконка-шум, что у ошибок сейчас.
- Картинки.
- Обычные блоки кода без `syntax` — исполняемый код живёт в `examples`, где для него есть вывод.

### 3.2. Нужно ли что-то ещё

- **Блок «Синтаксис» (` ```syntax `) — да, обязателен.** Сейчас шаблоны вроде `if items is None: items = []` рендерятся пропорциональным шрифтом без отступов, и их нельзя отличить от текста. Блок не исполняется и не нумеруется. Подсветка такая же, как в коде, плюс кириллица приглушённым цветом.
- **Таблица — да, но узкая.** Ровно для соответствий (JSON ↔ Python, режимы файлов, токены `re`, цена операций). Ограничения из §2.2 проверяются при сборке.
- **«Было/стало» в body — нет.** Для этого есть структурированные `pitfalls` (§2.5). Сравнение «цикл против включения» (`comp_list`) подаётся двумя примерами с `note`.
- **Ссылка на пример (якорь) — нет.** «Как в примере ниже» достаточно, номера примеров нестабильны.

### 3.3. Запрещённые символы

Причина: Onest не содержит части стрелок и значков. Android берёт глиф из системного fallback. Для символов со свойством Emoji это Noto Color Emoji, отсюда цветные квадратики. Проверено по cmap `Onest-Regular.ttf`: `↔` и `⇒` отсутствуют.

| Символ | Код | Проблема | Чем заменить |
|---|---|---|---|
| ↔ | U+2194 | Нет в Onest, Emoji | Таблица или «и обратно» |
| ⇒ | U+21D2 | Нет в Onest | «значит», «поэтому» |
| ➡ ⬅ ⬆ ⬇ | U+27A1, U+2B05, U+2B06, U+2B07 | Emoji | «→» только в тексте, или слово |
| ↩ ↪ ↕ | U+21A9, U+21AA, U+2195 | Emoji | Слово |
| ▶ ◀ ▸ | U+25B6, U+25C0, U+25B8 | Emoji / нет в Onest | Нумерованный список |
| ✔ ✅ ☑ | U+2714, U+2705, U+2611 | Emoji | Поле `good` или слово «правильно» |
| ✖ ❌ ❎ | U+2716, U+274C, U+274E | Emoji | Поле `bad` или слово «ошибка» |
| ⚠ ❗ ❓ ‼ ⁉ | U+26A0, U+2757, U+2753, U+203C, U+2049 | Emoji | `**жирный**` один раз, или ничего |
| ℹ ⭐ ⏱ ⌛ ✏ ✂ | U+2139, U+2B50, U+23F1, U+231B, U+270F, U+2702 | Emoji | Ничего |
| ◻ ◼ ▪ ▫ ⬛ ⬜ | U+25FB, U+25FC, U+25AA, U+25AB, U+2B1B, U+2B1C | Emoji | Маркер списка `-` |
| ∞ √ ⁿ | U+221E, U+221A, U+207F | Нет в Onest | `float("inf")`, `math.sqrt`, `n ** k` в коде |
| ‑ (неразрывный дефис) | U+2011 | Нет в Onest | Обычный дефис |
| U+FE0F | вариационный селектор | Принудительно включает эмодзи | Удалить |

Разрешено в тексте (есть в Onest): `→` (только между словами, не между кусками кода), `—`, `–`, `…`, `×`, `≤`, `≥`, `≠`, `≈`, `±`, `²`, `«»`, `„“`, `№`, `°`.

**Проверка при сборке** (в `topic()`), а не «по памяти»:
- каждый символ `title`, `summary`, `body`, `note` и `why` вне бэктиков должен быть в cmap `Onest-Regular.ttf`;
- внутри бэктиков и в коде — в cmap `JetBrainsMono-Medium.ttf`;
- плюс явный стоп-лист из таблицы выше.

Набор cmap генерируется один раз в `tool/content/glyphs.json`.

## 4. Ссылки между темами

### 4.1. Принцип

Ссылка отвечает на вопрос «а что это?» в момент, когда он возникает. Она не украшает текст и не рекламирует соседние темы.

**Что делать ссылкой:**
1. Конструкцию или функцию **из другой темы** при первой встрече в этой теме (`isinstance` в `rec_structures`, `@lru_cache` в `rec_memo`).
2. Термин, который объясняется в другом месте («замыкание», «хешируемый»).
3. **Всегда** — ссылку вперёд: всё, что в курсе позже текущего модуля. Сейчас именно они записаны как «в отдельном модуле».
4. Имена исключений при первой встрече.

**Что не делать ссылкой:**
- термин текущей темы;
- повторную встречу того же термина в этой теме;
- «базовый словарь» после модуля «Функции» (13-й): `print`, `input`, `=`, `if`, `for`, `while`, `len`, `range`, `int`, `str`, `list`, `def`, `return`, `True/False`. К этому моменту их знают, а ссылки на них — шум;
- код внутри `syntax`-блоков, примеров, `bad`/`good`;
- summary и заголовки;
- `note` примеров.

**Лимиты:** не больше 2 ссылок на абзац, 1 на пункт списка и 8 на тему. Если ссылок больше, текст объясняет слишком много чужого, и тему надо упростить.

**Ссылка вперёд** в шторке помечается: «Тема из модуля „Декораторы“, вы до неё ещё не дошли». Открыть её можно — это справочник, а не уровень.

### 4.2. Автоссылки

Автоссылки ставятся **при сборке, не в приложении.**
- `bclib.topic()` проходит по `` `код` ``-фрагментам body и `why`. Фрагмент сопоставляется с глоссарием: целиком или по ведущему идентификатору. `d.get(k, 0)` даёт `.get`, `json.dumps(text)` даёт `json.dumps`, `print(...)` даёт `print`.
- По правилам §4.1 фрагмент переписывается в ``[[id|`код`]]``.
- В `topics.json` попадает уже явная разметка, и Flutter-рендерер остаётся «тупым».
- Ручная ссылка автора всегда главнее. ``{`код`}`` (фигурные скобки вокруг чипа) отключает автоссылку.
- Сборка падает на неизвестном `topic_id`, ссылке на себя и превышении лимитов.

**Неоднозначные термины** (`in`, `*`, `/`, `|`, `.pop`, `.count`, `.copy`, `with`, `else`) автоматически не связываются. Только явной ссылкой, автор выбирает тему по смыслу.

Формат глоссария — `tool/content/glossary.py` → `assets/content/python/glossary.json`:

~~~python
term("dict.get", match=[".get(", "dict.get"], topic="dict_methods",
     brief="Значение по ключу; если ключа нет — значение по умолчанию, без KeyError.",
     example='d = {"чай": 3}\nprint(d.get("сок", 0))')
~~~

Шторка показывает `brief` и `example` (вывод считается так же, как у примеров). Без них — summary и первый пример темы.

### 4.3. Глоссарий: конструкция → тема

Все id взяты из `topics.json`. Колонка «Суть» — текст `brief` для шторки. «Явно» значит: только ручной ссылкой, автоссылки нет.

Решения по иерархии:
- **Кнопка «Сохранить в журнал» и карточка повторения уходят вниз**, а в AppBar остаётся иконка-закладка. Сейчас они занимают первый экран, а человек пришёл читать.
- **Код и вывод — одна доска.** Связь «этот код напечатал это» должна читаться без подписи. Отдельная подпись «Вывод» внутри доски остаётся маленькой, как метка терминала.
- **Пример озаглавлен своей `note`**, а не «Пример 2».
- **Номера строк в журнале убрать.** В «Найди баг» они нужны, здесь только съедают 26 dp ширины.
- **Ошибки — без иконки warning у каждого пункта.** Цвет полос «нельзя/можно» несёт смысл, иконка его дублирует. Красный и зелёный подкреплены словами, а не одним цветом.
- **«Примеры», «Частые ошибки», «Связанные темы» — titleLarge 20**, а разделы body — titleMedium 17. Это две разные иерархии: внутри объяснения и между блоками карточки.

### 5.2. Ссылка в тексте

- Обычный текст-ссылка: цвет `scheme.primary` (Python-синий `#2F6DB5` днём), подчёркивание 1 dp с отступом 2 dp. Контраст на `#FFFFFF` — 5,3:1, проходит WCAG AA.
- Ссылка-код: чип кода (фон `lineSoft`, текст `ink`) плюс подчёркивание primary 1,5 dp под чипом и текст чипа primary.
- Почему не жёлтый. Жёлтый `#FFD43B` в теме зарезервирован под награды (`app_colors.dart`: «Python yellow: rewards only»), а на белом у него контраст 1,5:1, он нечитаем как цвет текста. Жёлтый допустим только как фон «прочитано» в будущем, не для ссылок.
- Зона нажатия: `TextSpan` с `TapGestureRecognizer`. Строка 17 × 1,5 = 25,5 dp — меньше 48, поэтому ссылки в соседних строках не должны стоять друг под другом (это одна из причин лимита «2 на абзац»). Для доступности: `Semantics(link: true)`, озвучивается как «ссылка, тема Словари».

~~~python
topic("data_json", "JSON",

      """
      JSON — самый частый формат, в котором программы передают данные: ответы веб-сервисов, файлы настроек, сохранения в играх. Это обычный текст, который понимает почти любой язык программирования.

      ## Четыре функции

      Две работают со строками, две — с файлами. Буква `s` в конце значит string — строка.

      - `json.dumps(данные)` — данные Python в строку JSON
      - `json.loads(строка)` — строка JSON в данные Python
      - `json.dump(данные, файл)` — записать в открытый файл
      - `json.load(файл)` — прочитать из открытого файла

      Файл открывают через [[files_open|open и with]] с `encoding="utf-8"`.

      ## Как типы переводятся

      | Python | JSON |
      |---|---|
      | `dict` | объект `{}` |
      | `list`, `tuple` | массив `[]` |
      | `str` | строка `"…"` |
      | `int`, `float` | число |
      | `True`, `False` | `true`, `false` |
      | `None` | `null` |

      Обратно переводится не всё один к одному:

      - кортеж возвращается списком;
      - ключи словаря возвращаются строками: `{1: "a"}` станет `{"1": "a"}`.

      Множество, дату или свой объект `dumps` не переводит: будет `TypeError`. Их заранее превращают в список, строку или словарь.

      ## Строгий синтаксис

      JSON строже Python. Строки и ключи — только в двойных кавычках, `true` и `null` — со строчной буквы, запятая после последнего элемента запрещена. Текст `{'a': 1}` уже не JSON: `loads` выбросит `json.JSONDecodeError`.

      Неправильный JSON обычно приходит извне — от пользователя или из сети. Поэтому разбор оборачивают в [[exc_try|try / except]].

      ## Читаемый вывод

      По умолчанию `dumps` пишет всё в одну строку и заменяет русские буквы кодами вида `\\u0447`. Два параметра это меняют:

      - `ensure_ascii=False` — оставить русский текст как есть;
~~~

### 6.2. `cond_if` (модуль conditions)

~~~python
topic("cond_if", "if / elif / else",
      "`if` выполняет блок кода, только когда условие истинно; `elif` и `else` добавляют другие варианты.",
      """
      Программа не всегда должна делать одно и то же: скидка — только постоянным покупателям, «Верно!» — только при правильном ответе. Для таких развилок есть `if`.

      ## Как записать

      ```syntax
      if условие:
          действия
      elif другое_условие:
          другие_действия
      else:
          действия_иначе
      ```

      - В конце строки с условием — двоеточие.
      - Тело ветки пишут с отступом в 4 пробела. По отступу Python понимает, какие строки входят в ветку.
      - `elif` и `else` необязательны. `elif` может быть сколько угодно, `else` — один и только в конце.

      ## Как Python выбирает ветку

      1. Проверяет условие после `if`.
      2. Если оно ложно — проверяет условия `elif` по порядку, сверху вниз.
      3. Выполняет первую ветку с истинным условием, остальные пропускает.
      4. Если не подошло ни одно, выполняет `else`. Если `else` нет — ничего.

      **Выполняется не больше одной ветки.** Поэтому порядок важен: первыми ставят самые строгие условия.

      ## Что может быть условием

      Любое выражение, которое даёт `True` или `False`: [[ops_compare|сравнение]] `x > 0`, проверка `"а" in слово`, сочетание условий через [[ops_logic|and, or и not]].

      Можно написать и просто значение: `if name:` сработает, если строка не пустая. Какие значения считаются ложными — в теме [[types_bool|Истинность значений]].

      ## Цепочка или несколько if

      Каждый отдельный `if` проверяется сам по себе, даже если предыдущий уже сработал. `if` с `elif` — одна цепочка, в ней срабатывает одна ветка.

      Внутри ветки может быть свой `if` — с отступом ещё на уровень. Если нужно лишь выбрать одно из двух значений, есть короткая запись в одну строку — [[cond_ternary|условное выражение]].
      """,

            print("Жарко")
        print("Готово")""",

       ("""\
        score = 73
        if score >= 90:
            grade = "A"
        elif score >= 70:
            grade = "B"
        elif score >= 50:
            grade = "C"
        else:
            grade = "D"
        print(grade)""",
        "73 подходит и под >= 70, и под >= 50 — срабатывает первая"),
       ("""\
        score = 95

        if score >= 90:
            print("отлично")
        if score >= 50:
            print("зачёт")

        print("---")

        if score >= 90:
            print("отлично")
        elif score >= 50:
            print("зачёт")""",
        "Два отдельных if сработали оба, в цепочке — только первый"),
       ("""\
        age = 20
        has_ticket = False

        if age >= 18:
            if has_ticket:
                print("Проходите")
            else:
                print("Нужен билет")
        else:
            print("Только 18+")""",
        "if внутри ветки: второй отступ — второй уровень")],
~~~

### 6.3. `deco_basics` (модуль decorators)

~~~python
topic("deco_basics", "Как работает декоратор",
      "Декоратор — функция, которая принимает функцию и возвращает её дополненную версию; `@имя` над `def` применяет его.",
      """
      Иногда одно и то же действие нужно добавить ко многим функциям: записать в лог каждый вызов, замерить время, проверить права. Копировать этот код в каждую функцию долго, и легко ошибиться. Декоратор позволяет описать добавку один раз и подключать её одной строкой.

      ## На чём это держится

      Функция в Python — такое же значение, как число или строка. Её можно:

      - передать в другую функцию как аргумент;
      - создать внутри другой функции;
      - вернуть из функции как результат.

      Вложенная функция помнит переменные внешней — это [[scope_closure|замыкание]]. Декоратор использует все эти свойства сразу.

      ## Как записать

      ```syntax
      def декоратор(func):
          def wrapper(*args, **kwargs):
              действия_до
              result = func(*args, **kwargs)
              действия_после
              return result
          return wrapper
      ```

      - `func` — исходная функция.
      - `wrapper` — обёртка: новая функция, которая вызывает `func` и добавляет что-то до или после.
      - `*args, **kwargs` принимают любые аргументы и передают их в `func` без изменений, поэтому обёртка подходит к любой функции. Подробнее — в теме [[args_star|`*args` и `**kwargs`]].
      - `return result` обязателен: без него декорированная функция будет возвращать `None`.

      ## Что значит @

      Запись `@декоратор` над `def f` — то же самое, что строка `f = декоратор(f)` сразу после объявления. Имя `f` теперь указывает на обёртку, а исходная функция живёт внутри неё.

      **Декоратор вызывается один раз — когда Python выполняет `def`.** При каждом вызове `f()` работает уже обёртка.

      ## Имя исходной функции

      У обёртки своё имя — `wrapper`. Из-за этого `f.__name__`, справка `help(f)` и сообщения об ошибках показывают не ту функцию. `@functools.wraps(func)` над обёрткой копирует имя и описание исходной функции. Его ставят всегда.

      ## Несколько декораторов

      Декораторы применяются снизу вверх, начиная с ближнего к `def`: `@a` над `@b` над `def f` означает `f = a(b(f))`. При вызове первой срабатывает внешняя обёртка `a`.

      Декоратор с настройкой, например `@repeat(3)`, — это уже три уровня функций, о них в теме [[deco_params|Декораторы с параметрами]]. Готовые декораторы из стандартной библиотеки: [[prop_property|@property]], [[rec_memo|@lru_cache]], [[dc_basics|@dataclass]].
      """,
      [("""\
        def loud(func):
            def wrapper():
                print("до")
                func()
                print("после")
            return wrapper

        def hello():
            print("привет")

        hello = loud(hello)
        hello()""",
        "Декоратор без @: функция подменена обёрткой"),
       ("""\
        from functools import wraps

        def log(func):
            @wraps(func)
            def wrapper(*args, **kwargs):
                print("вызов", func.__name__, args)
                result = func(*args, **kwargs)
                print("вернула", result)
                return result
            return wrapper

        @log
        def add(a, b):
            return a + b

        total = add(2, 3)
        print(total * 10)
        print(add.__name__)""",
        "Обёртка передала аргументы и вернула результат; имя сохранил wraps"),
       ("""\
        def register(func):
            print("регистрирую", func.__name__)
            return func

        @register
        def start():
            print("старт")

        print("до вызова")
        start()
        start()""",
        "Декоратор сработал один раз — при def, ещё до вызовов"),
       ("""\
        def bold(func):
            def wrapper():
                return "<b>" + func() + "</b>"
            return wrapper

        def italic(func):
~~~
